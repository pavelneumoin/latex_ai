# Развитие библиотеки Неумошки

План от 7 октября 2026. Это проект следующих этапов, а не список уже работающих функций. Проверка сканов и генератор остаются закрыты в UI/API; новые платные вызовы не выполняются. Поставщик модели ещё не выбран.

## 1. Закончить библиотеку и выдачу комплектов

Первый следующий выпуск: владелец добавляет две настоящие ссылки на полные комплекты Яндекс Диска в `/admin/catalog`. Проверяем содержимое, скачивание из новой сессии владельца, обычного оплаченного аккаунта и отказ после окончания доступа. Ссылки на отдельный лист `/i/…` не заменяют комплект.

Готовность: для каждой карточки заданы предмет, авторский номер задания, тема/подтема, состав, несколько разрешённых превью; черновики скрыты. Экспорт витрины должен выполняться после редакторских изменений. Полные PDF и исходники не включаются в Git и не проксируются маленькой VM. Публичную ссылку Диска получатель может передать другому человеку: подписка контролирует выдачу ссылки сайтом, а не последующий доступ к публичному Диску. Для более строгой защиты потребуется отдельное приватное хранилище с временными ссылками — отдельное решение владельца.

Перед открытием самой библиотеки в интернете: обновить уязвимые зависимости с проверкой совместимости, завершить юридические документы, настроить выбранный способ входа и настоящий платёжный сценарий. Текущий mock-провайдер не должен принимать настоящие платежи. Школьная витрина может работать независимо, с ознакомительными страницами и честным состоянием открытия.

## 2. Версии листов и ручной пилот проверки

Сначала берём один авторский рабочий лист и 10–20 обезличенных примеров, которые владелец вправе обрабатывать. Фиксируем неизменяемую `MaterialVersion`: комплект, редакция PDF, SHA-256, идентификаторы заданий, страницы и области ответов. Эталон и критерии имеют отдельную версию и доступны только преподавателю. Не связывать скан с названием файла: оно неоднозначно.

Минимальный рабочий этап без оплаты AI: загрузка нескольких фотографий → ручной выбор версии листа и ученика/псевдонима → корректировка поворота/порядка → очередь на просмотр преподавателем → таблица заданий, баллов и комментариев → экспорт PDF/CSV. Учитель подтверждает итог; ошибку распознавания можно исправить. Существующие CheckJob/CheckResult — отправная точка, но их текущие поля не заменяют версионирование и аудит исправлений. Прогресс школьных заданий и статистику попыток автоматически не менять.

Критерий готовности: две работы разных учеников невозможно перепутать, повтор запроса не создаёт вторую проверку, новая версия эталона не изменяет старый отчёт. Плохой снимок помечается для повторной загрузки.

## 3. Распознавание и проверка с выбранной моделью

Процесс: показать учителю число страниц и предварительный расход → подтвердить объём → распознать текст/формулы и координаты областей → привязать к заданиям выбранной версии → сравнить точные ответы детерминированно, где это возможно → получить предложения по развёрнутому решению → выделить сомнительные места → обязательный просмотр учителем → сформировать итоговую версию отчёта.

Каждая строка содержит: исходную область скана, распознанный ответ, эталон/критерий, предложенные баллы, объяснение ошибки, уверенность и решение преподавателя. Неуверенное распознавание не считать математической ошибкой автоматически. Указания внутри скана/учебника — входные данные, а не команды для модели или инструментов. Модель не получает доступ к аккаунтам, платежам, чужим работам или серверной оболочке.

Интерфейс `ScanRecognitionProvider` принимает страницы и возвращает структурированные области/текст/уверенность/расход. `AssessmentProvider` принимает версии задания, критериев и подтверждённое распознавание. Их ответы проходят JSON-валидацию. Провайдер выбирается настройкой владельца; при отсутствии настройки возвращается `not_configured`, без скрытого переключения на платный сервис. Расход и качество измеряем на пилотной выборке до запуска продаж.

## 4. Рабочий лист по фотографии через Marp

Учитель загружает страницу, которую вправе использовать, выбирает тему, класс, объём и стиль. Распознавание показывает предварительный текст; преподаватель правит его и выбирает задания. Генератор предлагает структуру листа и отдельный ключ. После подтверждения создаётся Marp-документ по существующему шаблону, затем безопасный рендер PDF и превью. Учитель проверяет формулы, переносы, ответ и печатные поля перед сохранением версии. Ошибка рендера не выдаётся за готовый результат.

Первый объём: 1 фото → 1–2 страницы рабочего листа с ключом → ручная правка → PDF. Затем несколько фотографий, варианты и только после этого презентации. Не добавлять произвольные внешние HTML/скрипты в Marp и не выполнять код модели; ограничить файловые пути, сеть и время рендера. Оригинал фотографии и модельный результат хранятся отдельно, с указанием происхождения.

## Техническая основа для этапов 2–4

- `ProcessingJob`: владелец, вид, версия входа, idempotency key, статус, lease/heartbeat, попытки, срок, ошибка и ссылки на артефакты. Состояния: draft → queued → running → review → completed; cancelled/failed отдельно. Переходы атомарные; повторное выполнение не повторяет списание.
- Один фоновый worker на маленьком сервере, начальная конкурентность 1. Веб-запрос только ставит задание в очередь и возвращает ID. На первом этапе SQLite-очереди достаточно; Redis не нужен. Рендер вынести в ограниченный процесс. Большие изображения — в приватное объектное хранилище, превью — оптимизированный WebP.
- Стартовые ограничения для пилота: до 10 страниц, 2 МБ на картинку, ограничение пикселей после декодирования, общий лимит пользователя и тайм-аут задания. Конкретные лимиты уточняются по замерам качества/памяти. MIME проверяется по содержимому; изображения перекодируются, метаданные удаляются.
- `UsageLedger`: резерв, фактический расход, возврат неиспользованного резерва. Отдельные входные/выходные токены, страницы OCR, рендеры, идентификатор запроса провайдера. Деньги — целые минимальные единицы валюты, тариф со своей версией; не хранить float-баланс. При неизвестной цене автоматическая платная обработка закрыта. Повторное уведомление/ответ не списывает деньги дважды.
- Секреты провайдера только на сервере. Подписанные ссылки на сканы короткоживущие, доступ только владельцу работы и назначенному преподавателю. Фамилия ученика не входит в URL, публичный экспорт или журналы. Не использовать школьные пароли для внешних AI API.
- Предлагаемый срок хранения: исходные сканы 30 дней после подтверждения, временные рендеры 24 часа, результаты и версии — до удаления владельцем с заранее обозначенной политикой резервных копий. Перед запуском утвердить сроки. Удаление должно отзывать ссылки и выполнять фоновую очистку объектов; в журнале оставить обезличенные сведения об операции.
- Наблюдаемость: длина очереди, длительность этапов, ошибки, расход по провайдерам, доля работ с ручной правкой. Логи не должны содержать снимки, полные ответы учеников, токены или ключи. Ограничения расходов — на задание, пользователя и день, с остановкой очереди при превышении.

Контракты будущих обработчиков: `frontend/lib/future/teacher-processing-contracts.ts`. Это только типы, без запущенного worker, внешних вызовов или платежей.

## Небольшие улучшения после каталога

1. Избранное уже есть: добавить подборки «К следующему уроку» и заметку преподавателя, без отдельной социальной ленты.
2. Недавно просмотренное: 8–12 комплектов в браузере, очищаемый список, без передачи истории третьим лицам.
3. Печатная памятка по каждому комплекту: формат, диапазон страниц без ответов, масштаб, двусторонняя печать. Не генерировать второй тяжёлый PDF только ради кнопки.
4. Метки состава и обновлений: «есть ответы», «2 варианта», «исправлено», версия и дата. Не обещать автопроверку до её запуска.
5. Сохранённые фильтры и ссылка на подборку для коллег; затем пакетное добавление материалов из согласованного манифеста с предпросмотром изменений.
